# Инфраструктура: базовый тех-дизайн

Хостинг, деплой, мониторинг, логи. Площадка не выбрана; исследование — [research/hosting.md](../../research/hosting.md).

## Что должно быть у площадки

- Долгоживущий процесс с постоянными соединениями и без ограничения на время работы — либо примитив, который ведёт себя так же.
- Запуск игрового процесса в нескольких регионах и выбор региона при создании комнаты: комната живёт рядом со своими игроками.
- Хранилище для лобби и итогов с малой задержкой от игрового процесса. Конкретная база — за прослойкой доступа к данным, площадка её не диктует.
- Место под сбор логов и метрик.
- HTTPS с сертификатом: игровое соединение из браузера только по защищённому каналу, вход через Google требует HTTPS.

## Деплой

Код — GitHub. Сборка и выкладка — из GitHub Actions по пушу в основную ветку: собрать образ, выложить на сервер, перезапустить процесс. Перезапуск игрового сервера рвёт активные бои — в MVP допустимо, выкладка по согласованию.

## Мониторинг и логи

Стек: Vector (сборщик) принимает логи сервера и клиента (по HTTP) и складывает в ClickHouse; дашборды — Grafana. Образец с готовой схемой таблиц и дашбордами — `../nx/hw-all/local/`; поля адаптируются под игру (комната, игрок, тик, регион).

Метрики сервера: длительность тика, игроков и комнат онлайн, входящих/исходящих сообщений в секунду, отброшенных команд, задержка до каждого клиента. Ошибки клиента — через HTTP-приёмник с полями: пользователь, комната, версия клиента, браузер.

Grafana доступна агенту через MCP — дашборды и запросы можно проверять без браузера.

## Окружения

Локальное — docker compose: игровой сервер, хранилище, стек логов; в нём же гоняются интеграционные и сквозные тесты. Боевое — по итогам выбора площадки; второе окружение (стейдж) появится, когда появятся игроки, которых жалко.

# Нефункциональные требования

Что должно выполняться независимо от выбранного стека.

## Отклик

Приоритет номер один. Цель для MVP: от нажатия клавиши до видимой реакции своего танка — без заметной задержки (клиентское предсказание), чужие танки и снаряды — с задержкой не больше одного-двух сетевых интервалов. Серверный тик — 30 в секунду (как в движке `tank-arena`); частота рассылки состояния клиентам — отдельный параметр, подбирается по измерениям.

## Нагрузка

Одна комната — до 50 игроков. Каждый шлёт ввод каждый тик: 50 × 30 = 1500 входящих сообщений в секунду на комнату. Исходящий поток — состояние всем 50 клиентам с частотой рассылки; размер снимка растёт с числом танков и снарядов. Проектируется под это сразу: бинарный протокол, дельты вместо полных снимков, рассылка только того, что клиент видит.

Для MVP одновременно живёт одна-несколько комнат на одном сервере.

## География

Игроки не обязательно в одном месте: старт — офис на Кипре, дальше игра должна работать для игроков в Европе и Америке без заметной разницы в отклике. Это достигается серверами в нескольких регионах и созданием комнаты рядом с её игроками, а не одним сервером «где-то». Для MVP допустим один регион, но архитектура и площадка выбираются с учётом нескольких.

## Платформы

Браузер — база. Десктоп: Chrome, Firefox, Safari последних версий. Мобильные: Android Chrome, iOS Safari, сенсорное управление. Нативных приложений в MVP нет.

## Наблюдаемость

- Состояние сервера: загрузка процессора, длительность тика, число игроков и комнат, задержка до клиентов.
- Ошибки сервера и клиента собираются централизованно, просматриваются в одном месте с фильтрами по комнате, игроку, времени.
- Клиентские ошибки уходят на сервер сбора логов, не остаются в консоли браузера.

## Безопасность

Сервер авторитарен (ADR). Вход через Google. Античит как отдельная система — вне первой итерации, но протокол не должен давать клиенту права, которые потом придётся отбирать.

## Хранение

Учётные записи, комнаты, итоги боёв — долговременное хранилище; сессии, присутствие, быстрые счётчики — быстрое хранилище. Доступ — через прослойку, конкретные базы выбираются вместе с площадкой и могут меняться без правок игровой логики. Состояние боя — память игрового процесса.

## Тестируемость

Бэкенд проверяется снаружи через свои точки входа с полным покрытием; игра целиком — сквозными тестами в браузере; протокол и сервер — нагрузочными прогонами. Правила — [ADR тесты](../../adr/tests.md). Следствие для дизайна: каждый сценарий достижим через внешний интерфейс без ручной подготовки состояния.

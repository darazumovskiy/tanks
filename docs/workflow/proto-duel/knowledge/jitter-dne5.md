# Разбор журнала DNE5: «дёргание» танка на телефоне

Игра `DNE5` (2026-10-04 01:24–01:27 МСК), телефон Димы в приложении против манекена, задержка 70–150 мс. Файл — `/opt/tanks-logs/DNE5.log`. Дима назвал момент: раунд 2, на счётчике раунда 1:44 ± 5 с — это тик игры `gt` ≈ 2600–2700.

## Что видно

**Команды приходят на сервер пачками.** За игру из 4880 тиков: 3814 тиков с одной командой, 586 без команд, 410 с двумя, 42 с тремя, 24 с четырьмя и больше, один тик с тринадцатью. Типичный узор — `in1=2, in1=0, in1=2, in1=0`: соседние команды склеиваются по дороге и приезжают парой. Сервер применяет за тик одну последнюю команду, остальные выбрасывает (`room.ts`, «новое пересиливает старое») — около 12 % команд Димы на сервере не исполнились.

**Каждая выброшенная команда — рывок назад.** Клиент уже прошагал этот тик, сервер нет; следующий снимок возвращает танк на тик движения назад. В журнале клиента это `corr=5.9` (один тик хода на этой скорости) на каждом втором-третьем снимке в движении. Момент, который заметил Дима: `gt=2627–2636` — девять тиков сервер не получал команд (`ack1=2627` стоит), очередь клиента выросла до 7, затем шесть команд пришли одним тиком, сервер применил одну, клиент получил `corr=29.2` — прыжок на 29 единиц поля (счётчик раунда 1:46). Рядом `corr=11.7` (gt 2629) и `corr=12.3` (gt 2643).

**Снимки приходят пачками.** Интервалы между снимками у клиента: `gap=0, 0, 0, 175`, `gap=287`, `gap=220` вместо ровных 33 мс. Противник рисуется интерполяцией по времени прихода — поэтому замирает и прыгает.

**Пауза без команд до 400 мс.** `gt=2656–2668`: двенадцать тиков без команд, затем 13 одним тиком. Танк стоял, поэтому прыжка не было; в движении это был бы «телепорт» на 60 единиц.

**Не причина:** камера — режим `follow`, высота окна 765 всю игру, ступеней не было; кадры — 118–120 к/с, худший 8–17 мс, один кадр 58 мс при старте; сервер — опоздание тика до 22 мс дважды, молчание игрока (`sil1=1`) ни разу; процесс не перезапускался. Разрыв сокета один — `gt=4873` (02:42 игры), переподключение за секунду, после него новая игра `KXBY`.

## Причина

Сеть телефона отдаёт и принимает мелкие пакеты неравномерно (джиттер), а сервер и клиент рассчитаны на ровный поток: одна команда за тик без очереди, интерполяция по времени прихода, поправка применяется мгновенно. Камера тут ни при чём; совпадение с выкладкой камеры — первая игра с телефона в сети хуже офисной.

## Что дальше

Исправления в этой задаче не делаются. Тема вынесена в бэклог исследований план-карты (`workflow/roadmap.md`): сначала эмуляционные тесты сети, которые воспроизводят зафиксированные здесь узоры — пары команд в один тик, пауза 300–400 мс с последующей пачкой, снимки пачками по 3–4, — и считают поправку, долю выброшенных команд и замирания противника; затем выбор решения на этих тестах. Цифры из этого разбора — эталон для сценариев.

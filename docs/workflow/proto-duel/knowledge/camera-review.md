## 3. Логические дыры и противоречия

**3.1. Поглощающие состояния ступенчатого зума** (`camera.ts:119–126` + clamp `68`). Нужная высота всегда в [675; 900], а порог считается от зафиксированной. Для `c ∈ [750; 843,75]` ни одно значение нужной не выбивает порог — масштаб замирает до `resetCamera`. При выходе из 675 вверх фиксируется первое значение за порогом ≈ 811 — уже внутри ловушки, если танки разъезжаются постепенно. Практический сценарий: один раз сблизились, разъехались, второй раз сблизились (не до упора), разъехались — камера застыла на ~829 и до конца раунда ни «центр событий», ни «поле целиком» не наступают. Правило `isFullyOut` (`73`) при этом недостижимо, потому что из любого `c < 900` до 900 нужно `c < 750`.

**3.2. Первая ступень вниз даёт 720 → ширина 1601.** Порог из 900 — нужная < 720; фиксируется 719–720, ширина 1601 > 1600. Окно шире поля на 1 единицу, но `isFullyOut` ложь → центрируется пара → пустота ≥ 1 всегда с одной стороны и перескакивает на другую при пересечении парой x = 800. Это и есть «1601 против 1600», причина — не настройка 75 %, а то, что ступень берёт нужную высоту в точке пересечения порога (`125`), а не тянет к минимуму.

**3.3. Полное отдаление → приближение: разрыв цели.** В момент `committed` 900 → 719 целевой центр прыгает с (800, 450) на (центр пары x, pairY − 0,09·719 … ) (`75–76`), высота догоняет за 600 мс, центр — за 300 мс (`141–152`): разные скорости → отображаемая камера идёт по дуге, безопасная область в пути не соблюдается, `keep…` к сглаженной камере не применяется вовсе (`renderer.ts:146,152`).

**3.4. `keepTargetOutOfThumbZones` против центрирования и против противника.** Функция принимает один `target` (`94`), сдвигает окно без проверки второго танка и без ограничения по полю: (а) правило «под панелями» (`97–99`) при полном отдалении уводит нижние 84 ед. поля с противником (диагональ); (б) горизонтальный сдвиг доводит противника до fx 0,98; (в) при зафиксированной высоте 829 — противник за кадром. Центрирование пары (I5) и зона пальца конфликтуют всегда, когда я — нижний и боковой в паре: я на (fx 0,12…0,32; fy 0,5…0,68) — это разрешено `FRAMING_INSETS`, но запрещено `THUMB_ZONES` (0,32 ≫ 0,12), т.е. две ступени конвейера спорят о допустимом месте танка.

**3.5. Выбор оси без гистерезиса** (`107–109`). Линия переключения `shiftX = 1,5·shiftY`; для танка у стенки x = 140 при полном отдалении — y = 650. Танк, покачивающийся ±2 ед. вокруг 650, каждый кадр меняет цель между (−200, 199) и (−500, 0); со сглаживанием 300 мс камера ползает по отрезку между ними — это и есть дрожание. Усугубляется тем, что `shiftY` растёт 1:1 с движением вниз (режим y), а `shiftX` фиксирован положением у стенки.

**3.6. Спавн на границе зоны.** Спавн (140, 450) при полном отдалении — fy ровно 0,500, fx 0,17 (внутри боковой полосы). Любой сдвиг вниз на 1 ед. включает режим y. Поле «уезжает» вверх вслед за танком: на 150 вниз — 150 пустоты снизу, хотя по бокам простаивает по 200 пустых единиц, которые режим x мог бы использовать без потери поля (при `x = −500` поле режется справа — тоже плохо, см. 3.4).

**3.7. Вертикальная безопасная полоса слишком тонкая.** 0,54·675 − 220 = 144 ед. (2,25 длины танка). `TARGET_MARGIN` 110 входит дважды, по 3,4 радиуса танка с каждой стороны. Любой вертикальный манёвр > 217 ед. при 675 требует отдаления; при 900 полный вид наступает уже при dy > 266. Зум практически не зависит от горизонтали (запас 920 ед.) — «постоянный зум» идёт от вертикали.

**3.8. Правило «под панелями» применяется ко всей ширине**, хотя панели — только углы и таймер по центру; при полном отдалении оно сдвигает окно, когда я у верхней стенки (y < 108), пряча низ поля.

**3.9. Противник мёртв → приближение к себе** (`renderer.ts:134`). В дуэли смерть = конец раунда (`round.ts:522`), камера за 2 с уезжает к 675 вокруг меня, в углу — больше половины экрана пустота под оверлеем итога. Решение не зафиксировано ни в одном документе.

**3.10. Документы противоречат друг другу и коду.**
- `decisions.md:33`: в одном пункте «центрирует пару даже ценой пустоты» и «пустота за полем — только если свой танк уехал бы под стик».
- `mobile-screen.md:9`: «любое приближение — центр событий, даже если … пустота» и через фразу «это единственный случай пустоты» (про зоны пальцев).
- `mobile-screen.md`, таблица файлов: `keepTargetInSafeZone` — такой функции нет.
- `mobile-screen.md`, строка плана «сдвиг по x до 24 %; подъём до 55 %» — тестовые значения, боевые 32 %/50 %.
- `settings.ts:40–45`: диапазон 50–100, `decisions.md:28` — «40–100 %».

## 4. Структура сценарного теста

**Предпосылка.** Конвейер живёт в `Renderer.frameBattle` (`renderer.ts:123–154`), которому нужен canvas, а константы `FRAMING_INSETS`, `THUMB_ZONES`, `ZOOM_DEAD_BAND`, `ZOOM_OUT_RATIO` не экспортированы. Чтобы тест гонял боевой код, вынести чистую часть в `camera.ts`:

```ts
export interface DuelCameraConfig {
  insets: FramingInsets;
  zones: ThumbZones;
  deadBand: number;
  zoomOutRatio: number;
  minViewHeight: number;
}
export const DUEL_CAMERA: Omit<DuelCameraConfig, 'minViewHeight'> = { /* боевые константы */ };

export interface DuelCameraState { smoothed: Camera | null; committedHeight: number | null; }

export function planDuelCamera(
  state: DuelCameraState,
  me: Point,
  enemy: Point | null,
  screen: { width: number; height: number },
  config: DuelCameraConfig,
  smoothing: CameraSmoothing,
  dtMs: number,
): { state: DuelCameraState; wanted: Camera; camera: Camera }
```

`Renderer` хранит `DuelCameraState` и вызывает `planDuelCamera`; `resetCamera` обнуляет состояние.

**Таблица сценариев** — массив объектов:

```ts
interface Scenario {
  name: string;
  frames: Array<{ me: Point; enemy: Point | null; holdMs: number }>; // траектория: позиции и сколько держать
  minViewPercent?: number;        // по умолчанию 75
  expectMode?: 'fullyOut' | 'zoomedIn';
  tolerances?: Partial<Tolerances>; // где намеренно допускаем пустоту
}
```

Траектория из нескольких точек покрывает и предысторию (`committedHeight`), и сходимость после каждого шага. Минимальный набор: все строки таблицы из §2 плюс:
- `startDriveDown`: (140,450) → (140,600) → (140,649) → (140,651) → (140,700), по 3 с на точке;
- `jitterOnSwitchLine`: (140,648) ↔ (140,652) каждый кадр 2 с — проверка дрожания;
- `approachSeparateTwice`: нужная высота 900 → 675 → 900 → 675 → 900 через серию позиций по x при y = 450, затем старт-позиции — проверка I6 (ожидание: в конце `committedHeight === 900`);
- `deadBandEdge`: разнос по x 1000 → 995 → 1000 (порог 996) — ступень срабатывает один раз, без дребезга;
- `newRound`: любая позиция → `reset` → спавны: первый кадр равен цели.

**Прогон.** Для каждого экрана × сценария: `state = {smoothed: null, committedHeight: null}`; для каждой точки траектории — `holdMs / 16` кадров `planDuelCamera(..., dtMs = 16)` с боевыми `smoothing` `{300, 600, 300}`. После каждой точки:

1. сходимость: `|camera.center − wanted.center| < 1`, `|camera.height − wanted.height| < 1` (иначе 3 с мало — само по себе сигнал);
2. `checkInvariants(wanted, me, enemy, screen, config)` → список нарушений строками вида `"I1: enemy fy=1.067"`; `expect(violations).toEqual([])`;
3. по всей траектории: `maxCenterStepPerFrame ≤ k·maxTargetJump` и — для `jitter*` — размах `camera.x` за последнюю секунду < 5 ед.

**`checkInvariants`** считает доли экрана через `worldToScreen`/размер окна и проверяет: I1 (противник в окне с запасом радиуса танка 24), I2 (зона пальца по боевым `zones`), I3, I4 (при `height ≥ 900`: `|x + w/2 − 800| < 1`, `y = 0`), I5 (при `height < 900` и `mode === none`: центр пары в (0,5; 0,41) ± 0,01), I10 (пустота по каждой стороне ≤ допуск сценария; по умолчанию допуск — только симметричная пустота полного отдаления `(w − 1600)/2`), I12 (не обе стороны одной оси сразу при `w < 1600`).

**Сетка вместо ручного перебора.** Отдельный тест `it.each(screens)('сетка позиций')`: `me`, `enemy` ∈ {24, 140, 400, 800, 1200, 1460, 1576} × {24, 140, 450, 760, 876} (35 точек → 1225 пар), без предыстории и с предысторией `committedHeight ∈ {675, 720, 829, 900}` — около 5000 прогонов конвейера на экран, миллисекунды. Собрать нарушения в массив и падать с первыми 20 строками — это даёт контрпримеры в координатах поля автоматически, как в §2.

**Сходимость как инвариант сглаживания.** Для статичной сцены после 188 кадров ошибка экспоненциального догона с lag 600 — 0,5^(3000/600) = 3 % пути; при скачке высоты на 225 ед. это 7 ед. — поэтому для `height` допуск 8 ед. или держать 5 с.

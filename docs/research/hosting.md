# Хостинг игрового сервера

Вопрос: где живёт игровой процесс так, чтобы игроки в разных частях света получали минимальную задержку, а инфраструктура не требовала постоянного администрирования. Это одно из ключевых решений проекта; документ собирает факты и рамку исследования. Решение не принято.

## Что определяет выбор

**География.** Задержка сети задаётся расстоянием: Европа ↔ восток США — 80–100 мс в одну сторону, это уже заметно в бою. Один сервер в одном месте годится только для игроков из одного региона. Чтобы играть и в Европе, и в Америке, нужен сервер в каждом регионе и правило «комната создаётся рядом с игроками» (по географии создателя или большинства). Это требование к площадке: уметь поднять процесс в нескольких регионах и выбрать регион при создании комнаты.

Для MVP игроки — офис на Кипре. Своих подходящих хостингов на Кипре не ожидается; ищется ближайший быстрый регион. Кандидаты по географии и магистралям, проверяются замером из офиса: Афины (локальные провайдеры и точки присутствия edge-сетей), Милан и Франкфурт (регионы всех крупных облаков и контейнерных платформ), Тель-Авив (Azure, AWS, GCP), Стамбул, Нюрнберг/Фалькенштайн (Hetzner). Cloudflare заявляет точку присутствия на самом Кипре — проверить, куда реально размещается Durable Object с подсказкой региона.

**Модель процесса.** Игровой процесс долгоживущий, держит WebSocket-соединения и состояние в памяти (ADR). Площадка должна либо давать такие процессы, либо давать примитив, который ведёт себя так же с оговорками (Durable Objects на Cloudflare).

**Хранилище.** Логика пишется через прослойку доступа к данным, поэтому конкретная база — не критерий отбора площадки: подойдёт и MySQL, и Postgres, и SQLite-подобные облачные базы, и key-value. Критерий — задержка от игрового процесса до хранилища на операциях лобби и итогов, и удобство эксплуатации.

**Нагрузка комнаты.** До 50 игроков, ввод каждый тик (30/с) — 1500 входящих сообщений в секунду на комнату; рассылка 20–30 снимков в секунду каждому. Площадка должна тянуть это на одну комнату и масштабироваться числом комнат.

**Эксплуатация.** Инфраструктура — слабая зона команды. Чем меньше ручного администрирования (обновления ОС, сертификаты, падения машин), тем лучше.

**Цена.** Предпочтение — постоянно работающий сервер за предсказуемую месячную сумму (ориентир до €100–200 в месяц), а не оплата по использованию с открытым счётчиком. Почасовая тарификация облаков с месячным потолком этому не противоречит; модели вроде «за запрос» или «за секунду вычислений» без потолка — минус.

## Кандидаты

| Класс | Примеры | Как решает географию | Что известно |
|---|---|---|---|
| Edge-платформа с состоянием | Cloudflare Durable Objects | Объект создаётся с подсказкой региона рядом с игроком; сеть Cloudflare — сотни точек | Один объект — один поток, потолок ~500–1000 сообщений/с (наши 1500 — на грани; пакетирование ввода в одно сообщение на несколько тиков снимает вопрос). Спящие WebSocket. Нет WebTransport. Хранилище — D1 (SQLite), KV, диск объекта; есть готовый SDK Tikron под эту модель. В `alp-finder` уже есть аккаунт и опыт `wrangler` |
| Контейнеры по регионам | Fly.io, Railway, Render, Koyeb | Один образ, запуск в выбранных регионах; маршрутизация по близости | Обычный долгоживущий Node-процесс, любой транспорт, своя или управляемая база. Ближе всего к «своя машина, но без администрирования и с регионами» |
| Большое облако | AWS / GCP / Azure: виртуалки или контейнеры в регионах; AWS GameLift как специализированный сервис для игровых серверов | Регионы по всему миру, GameLift сам разводит сессии по флотам | Максимум возможностей и максимум сложности; GameLift — промышленный стандарт для сессионных игр, но ориентирован на бинарные серверы и большой масштаб |
| Своя машина | VPS / выделенный сервер (Hetzner, DigitalOcean и подобные) | Отдельная машина в каждом регионе, маршрутизация своя | Полный контроль, низкая цена, всё администрирование наше. Для одного региона — простейший путь |
| Оркестратор | Kubernetes + Agones (оркестратор игровых серверов) | Кластер в каждом регионе | Для многих комнат на многих машинах; для MVP избыточен, для ладдера — кандидат |

Гибриды нормальны: статика клиента и вход — на одной площадке, игровые процессы — на другой.

## Замер из офиса, 2026-10-01

Из офисной сети в Никосии (Cyta, AS6866), ICMP-пинг 6 пакетов и время установки TCP-соединения (≈ одно «туда-обратно») до публичных адресов провайдеров. Значения — миллисекунды туда-обратно, минимум/среднее.

| Куда | RTT, мс | Источник |
|---|---|---|
| **Cloudflare, точка LCA (Ларнака)** | **6 / 10–15** | `1.1.1.1`, `cdn-cgi/trace` показывает `colo=LCA` |
| Париж: Vultr, Scaleway | 51 / 54 | ICMP |
| Милан: Azure Italy North | 52 | TCP (ICMP закрыт) |
| Франкфурт: Vultr | 56 / 62 | ICMP |
| Страсбург, Гравлин: OVH | 57 / 62 | ICMP |
| Афины: GR-IX | 58 / 60 | ICMP |
| Цюрих: AWS | 59 | TCP |
| Амстердам, Мадрид: Vultr | 62 / 64 | ICMP |
| Нюрнберг, Фалькенштайн: Hetzner | 64 / 66, 67 / 70 | ICMP |
| Франкфурт, Милан: AWS | 65 | TCP |
| Лондон: Fly.io anycast (сам выбрал `lhr`) | 61 / 69 | ICMP |
| Стамбул: TurkNet | 73 / 76 | ICMP |
| Варшава: Vultr | 74 / 78 | ICMP |
| Ирландия: AWS | 79 | TCP |
| Стокгольм: Vultr | 84 / 86 | ICMP |
| Тель-Авив: AWS, Vultr | 95, 113 / 114 | TCP, ICMP |
| Хельсинки: Hetzner | 97 / 102 | ICMP |
| Вашингтон, Вирджиния: Hetzner, AWS | 132, 139 | ICMP, TCP |
| ОАЭ: AWS | 160 | TCP |

Что это значит:

- **До любого европейского сервера — 50–70 мс туда-обратно, пол — около 50.** Кипрский трафик уходит в Европу по подводному кабелю через Марсель, поэтому Париж и Милан быстрее Афин и Тель-Авива; географическая близость обманывает. Разница между Парижем, Миланом, Франкфуртом и Цюрихом — 10–15 мс, провайдера внутри этой группы можно выбирать по другим критериям.
- **50 мс — это полтора тика при 30 тиках в секунду.** Для схемы с предсказанием своего танка это рабочая зона (шутеры живут на 50–80 мс), но «мгновенного» отклика без предсказания не будет нигде за пределами Кипра.
- **Единственный путь к однозначным миллисекундам — вычисления на самом Кипре.** Cloudflare держит точку в Ларнаке (6–15 мс), но Durable Object — объект с состоянием — размещается не в любой точке, а в ближайшей из тех, где поддерживается; куда реально сядет объект для Кипра — проверяется только деплоем пробного объекта. Вторая возможность — сервер физически на Кипре: кипрский VPS или машина в офисной сети (для «сыграть в офисе» это < 5 мс; снаружи достижима через туннель, например Cloudflare Tunnel).
- Fly.io anycast сам отправил Кипр в Лондон (69 мс); при явном выборе региона `cdg` (Париж) ожидается ~52 мс — anycast-платформы надо проверять с явным регионом.
- Америка из офиса — 130–140 мс: для общих комнат Кипр ↔ США нужен сервер посередине или раздельные комнаты по регионам.

## Проба Cloudflare Durable Objects из офиса, 2026-10-01

Задеплоен отдельный Worker `tanks-probe` (аккаунт тот же, что у `alp-finder`, но воркер независимый): один Durable Object на имя комнаты, эхо по WebSocket, объект сам сообщает свой дата-центр через `cdn-cgi/trace`. Клиент на Node из офиса: новая комната на каждый прогон, 60 сообщений с шагом 100 мс. Код пробы — `/tmp/tanks-probe/` (worker.js, wrangler.toml, measure.mjs); воркер оставлен развёрнутым для следующих замеров.

| Подсказка региона | Край (Worker) | Где сел объект | WebSocket туда-обратно, мс: мин / медиана / p95 |
|---|---|---|---|
| нет | MRS Марсель | MXP Милан | 57 / 60 / 73 |
| нет | LCA Ларнака | CDG Париж | 54 / 61 / 86 |
| нет | MRS Марсель | MXP Милан | 52 / 54 / 64 |
| `weur` Западная Европа | LCA | CDG Париж | 55 / 90 / 298 |
| `weur` | LCA | AMS Амстердам | 62 / 71 / 131 |
| `weur` | LCA | CDG Париж | 57 / 61 / 99 |
| `eeur` Восточная Европа | LCA | FRA Франкфурт | 61 / 76 / 137 |
| `me` Ближний Восток | MRS | FRA Франкфурт | 61 / 68 / 102 |

Что это значит:

- **На Кипре объект не размещается.** Край Cloudflare отвечает из Ларнаки или Марселя, но сам объект всегда уезжает в Милан, Париж, Амстердам или Франкфурт — куда именно, меняется от прогона к прогону даже без подсказки. Подсказка «Ближний Восток» даёт Франкфурт. Надежда на 10 мс через Cloudflare закрыта.
- **Пол тот же, что у любого европейского сервера:** медиана 54–61 мс, это сырой пинг до того же города плюс 3–8 мс на путь через край Cloudflare. По минимальной задержке Cloudflare не выигрывает и не проигрывает VPS.
- **Разброс заметный.** p95 от 64 до 137 мс, редкие выбросы 150–500 мс; в одном прогоне по уже «тёплой» комнате — одиночный выброс почти 4 секунды. Сырой пинг до тех же городов в то же время держал разброс 2–3 мс, так что источник разброса — путь через Cloudflare или сам объект, а не офисная сеть. Для игры с тиком 33 мс выброс в 150 мс — пропуск четырёх-пяти тиков, это видно глазом. Нужно сравнение с эхо-сервером на обычном VPS в том же городе в то же время, прежде чем делать вывод «Cloudflare дёргает».
- **Первое обращение к новой комнате — 0,5–0,7 с** (создание объекта). Для входа в лобби терпимо.

Промежуточный итог: преимущество Cloudflare для нас — не задержка, а отсутствие серверов и администрирования. Единственный путь к однозначным миллисекундам для офиса — сервер физически на Кипре.

## VPS против Cloudflare в одно время, ночь 2026-10-02 (03:00 по Кипру)

Две машины Akamai (Linode) Nanode 1 GB: Милан `it-mil` и Париж `fr-par-2`, на каждой тот же эхо-сервер на Node без зависимостей (`/tmp/tanks-probe/vps-echo.mjs`). Клиент — тот же `measure.mjs` из офиса в Никосии, прогоны чередовались: Милан → Париж → Cloudflare, три круга по 60 сообщений с шагом 100 мс, затем два круга по 300 сообщений с шагом 33 мс (игровой тик).

| Куда | Шаг 100 мс: мин / медиана / p95, мс | Шаг 33 мс: мин / медиана / p95, мс |
|---|---|---|
| VPS Милан | 49 / 51–52 / 58–60 | 49 / 51 / 61–62 |
| VPS Париж-2 | 52 / 53 / 60–65 | 52 / 53–54 / 62–65 |
| Cloudflare DO → CDG Париж | 53 / 55 / 67–68 | 53 / 55 / 64 |
| Cloudflare DO → FRA Франкфурт | 59 / 61 / 72 | 62 / 67 / 75 |
| Сырой ICMP до VPS Милан / Париж | 49 / 52 / — (σ 3,6) и 52 / 58 / — (σ 6,3) | |

Что это значит:

- **Cloudflare добавляет 3–4 мс к медиане** относительно VPS в том же городе (Париж: 55 против 53) — цена пути через край. Когда объект уезжает во Франкфурт, добавка 10–15 мс. По задержке Cloudflare и VPS — один класс.
- **Разброс ночью одинаковый у всех:** p95 на 8–12 мс выше медианы и у VPS, и у Cloudflare; выбросы до 80–110 мс есть везде. Дневные выбросы Cloudflare (p95 до 300 мс в первой пробе) ночью не повторились. Чтобы закрыть вопрос «кто дёргает днём», нужен дневной повтор этой же пары.
- **Игровой ритм (30 сообщений в секунду по одному соединению) ничего не ухудшает** ни у VPS, ни у Cloudflare.
- **Милан на 2 мс быстрее Парижа** из Кипра. Разница в пределах шума; оба — одинаково хорошие кандидаты.
- Первый HTTP-запрос к VPS — 105–150 мс; к новому объекту Cloudflare — 450–600 мс.

## VPS против Cloudflare днём, вечер 2026-10-02 (19:45–19:55 по Кипру, рабочая сеть офиса)

Та же пара машин Akamai и тот же воркер, тот же `measure.mjs` из офиса; миланская машина к этому времени уже несёт игровой сервер на 8080, эхо переехало на 8081. Три круга по 60 сообщений с шагом 100 мс, затем четыре круга по 300 с шагом 33 мс; порядок в круге — Милан → Париж → Cloudflare. Параллельно ICMP до обеих машин и до ближайшего края Cloudflare (`1.1.1.1`, Ларнака).

| Куда | Шаг 100 мс: мин / медиана / p95, мс | Шаг 33 мс (три чистых круга): мин / медиана / p95, мс |
|---|---|---|
| VPS Милан | 48 / 51–52 / 58–63 | 48 / 51 / 57–59 |
| VPS Париж-2 | 52 / 54–55 / 65–76 | 51 / 54–55 / 65–75 |
| Cloudflare DO → CDG Париж | 55 / 61 / 107 | 53–54 / 57–60 / 67–103 |
| Cloudflare DO → MAD Мадрид | 58 / 62 / 71 | — |
| Cloudflare DO → FRA Франкфурт | 62 / 68 / 105 | 61 / 67 / 121 |
| Сырой ICMP: Милан / Париж / край Ларнака | 49 / 51 (σ 2,2); 51 / 56 (σ 3,7); 6 / 10 (σ 3,4) | |

Один из четырёх кругов на тике просел у всех трёх целей одновременно (медианы 62–95 мс, p95 283–450 мс, выбросы до 1,2–2 с у VPS) и через минуту прошёл — это офисная сеть, не серверы; в таблице он исключён.

Что это значит:

- **Медианы днём те же, что ночью:** Милан 51, Париж 54–55, Cloudflare 57–68. Суточного хода на самом пути нет.
- **Хвост днём у Cloudflare длиннее.** В чистых кругах p95 у VPS не поднимается выше 76 мс (Милан — 63), у Cloudflare в четырёх чистых прогонах из шести p95 — 103–121 мс, максимумы 125–400 мс. Ночью такой разницы не было. Вопрос «кто дёргает днём» закрыт: источник дневного разброса в первой пробе — путь через Cloudflare или сам объект, а не только сеть офиса; офисная сеть добавляет свои редкие провалы, но они бьют по всем целям одинаково.
- **Объект продолжает кочевать:** за семь прогонов без подсказки сел в Париж, Мадрид и Франкфурт. Мадрид — новая точка, на 10 мс медленнее Парижа.
- **Милан стабильнее Парижа и днём:** σ сырого пинга 2,2 против 3,7 мс, p95 на тике 57–59 против 65–75.

Итог замеров для MVP: сервер пробы — VPS в Милане; парижская машина больше не нужна. Cloudflare Durable Objects остаются кандидатом только за счёт отсутствия администрирования, по задержке они проигрывают VPS на 5–15 мс медианы и на 30–50 мс p95.

## План исследования

1. География MVP зафиксирована: Кипр. Америка — критерий следующих этапов.
2. Пинг до регионов, проба Durable Objects, VPS против Cloudflare ночью и днём — сделано.
3. Cloudflare Durable Objects под нагрузкой: синтетика на 50 клиентов с вводом 30/с на `tanks-probe`, длительность тика, потери, пакетирование ввода.
4. Кипр локально: есть ли VPS или колокация на острове с нормальной сетью; машина в офисе как вариант для MVP «в офисе».
5. Прикинуть стоимость каждого варианта на MVP (одна-три комнаты, часы игры в неделю) и на этап «несколько комнат в двух регионах».
6. Свести в таблицу по критериям выше и принять решение в `decisions.md`; при равенстве — предпочесть вариант с меньшей эксплуатацией.

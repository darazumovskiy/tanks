# Технология клиента на телефоне: WebView и альтернативы

Вопрос Димы (2026-10-03): не ограничивает ли WebView визуал и производительность; «серьёзные игры так не делают». Ответ — для нашего жанра нет; ниже почему и какие ступени есть, если упрёмся.

## Что такое WebView сегодня

Встроенное в приложение окно браузера. Репутация «для маленьких» — из 2012–2015: до Android 4.4 это был отдельный старый движок без ускорения графики и с медленным JavaScript. С Android 5 WebView — сам Chrome, обновляется через Play независимо от прошивки, рисует через видеочип. На iOS WKWebView — движок Safari с полной скоростью JavaScript. Игры на этой основе: Telegram Mini Apps, Facebook Instant Games, мобильные сборки Phaser/PixiJS-игр с десятками миллионов установок. Нативный код выигрывает в 3D и при тысячах объектов в кадре; наш жанр — вид сверху, два танка, десятки снарядов и частиц.

## Что в наших наблюдениях не про WebView

| Наблюдение | Настоящая причина | Где чинится |
|---|---|---|
| «Мыльно, нечётко» | Плотность отрисовки ограничена 2 пикселями на CSS-пиксель при 3 у телефона; спрайты — векторные заготовки без художника; шрифты без подгонки | Поднять плотность после замера кадров на устройстве; арт и типографика |
| «В нативных играх больше информации на том же экране» | Дизайн интерфейса: размеры, контраст, иерархия, иконки | Дизайн панелей — одинаково решается в вебе и нативе |
| «Подлагивает при стрельбе в движении» | Подозрение: фильтры холста в каждом кадре (убраны 2026-10-03); подтверждения на устройстве нет | Замер на телефоне через adb; дальше — по данным |

## Ступени технологии клиента

| Вариант | Даёт | Теряем | Когда переходить |
|---|---|---|---|
| **Canvas 2D в WebView** (сейчас) | Простейший код; один клиент на компьютер, Android, iOS; движок общий с сервером | Объекты рисуются по одному; потолок — несколько тысяч объектов в кадре | — |
| **WebGL в том же WebView** (PixiJS или свой слой) | Спрайты и частицы пакетами на видеочип, шейдеры для эффектов, запас производительности на порядок; меняется только слой рендера, остальное (движок, сеть, предсказание, ввод) как есть | Больше кода в рендере, ещё одна зависимость (M) | Когда замер на устройстве покажет, что Canvas 2D не держит 60 к/с при нужном числе объектов |
| **Нативный клиент** (Unity, Godot, Kotlin + Swift) | Максимум производительности и системных API | Движок пишется второй раз на другом языке и должен совпадать с серверным побитово (L на порт + постоянная цена на каждое изменение правил); два клиента вместо одного (XL) | Если потребуются системные возможности, которых в вебе нет. Изометрия и 3D нашего масштаба на three.js идут в том же WebView — [3d-pipeline.md](3d-pipeline.md) |
| **Движок на Rust/C++ → WASM для веба + натив** | Один движок и в нативе | Движок переписывается на другой язык с тестами детерминизма против текущего (L), клиентов становится два (XL); каждое изменение правил проходит через оба стека | Нет оснований в обозримом плане |

## Вывод

Общий движок и один клиент на все платформы не блокируют ни визуал, ни производительность для дуэли и office-match. Ощущение «неуютно» лечится настройкой управления, камеры, обратной связи (вибрация, звук) и дизайном интерфейса — всё внутри текущей технологии. Следующая ступень при нехватке производительности — WebGL внутри того же WebView, без потери общего движка. Решение пересматривается по замерам на устройстве, не по ощущениям.

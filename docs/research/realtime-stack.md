## Сервер

Три пути.

| Путь | Что даёт | Чем платим |
|---|---|---|
| **Node.js / TypeScript, свой цикл** на `ws` или `uWebSockets.js` | Движок `tank-arena` уже на JS — переносится без переписывания, один язык и один модуль движка на сервере и клиенте (это условие корректного предсказания на клиенте). Серверы diep.io-класса (DiepCustom) работают так: TypeScript, uWebSockets, 25 тиков/с, бинарный протокол, тысячи сущностей | Одно ядро на процесс: одна комната = один процесс или воркер; масштаб — по комнатам, не внутри комнаты. Для 50 танков и сотен снарядов при 30 тиках/с — запас большой |
| **Colyseus** (Node, MIT) | Готовые комнаты, матчмейкинг, переподключение, синхронизация состояния по схеме, клиенты для браузера и движков, обучающие примеры с предсказанием и компенсацией задержки | Синхронизация состояния универсальная (дифф по схеме), для шутера с 50 танками и роем снарядов свой бинарный снимок компактнее и быстрее; часть фреймворка окажется лишней. Опыт: лучше брать идеи и, возможно, слой комнат, не весь стек |
| **Go или Rust** | Сырая производительность, многопоточность внутри комнаты. Nakama (Go) — целая платформа: учётки, друзья, таблицы, матчи | Движок придётся держать в двух реализациях (сервер на Go/Rust, клиент на JS) и доказывать их побитовое равенство — главный риск для предсказания на клиенте. Nakama — большой продукт под другой масштаб |

**Вывод по серверу.** Один язык на обе стороны перевешивает всё: TypeScript, Node.js, свой игровой цикл, минимум зависимостей. Colyseus — источник образцов для комнат и компенсации задержки. Если профилирование покажет упор в CPU внутри одной комнаты — вынести горячие части в WebAssembly (AssemblyScript или Rust) с тем же модулем на клиенте; это сохраняет единственность движка.

### Как Node держит большой онлайн

Node исполняет JavaScript в одном потоке: один процесс — одно ядро. Это ограничение одной комнаты, а не всего онлайна. Схема масштабирования, по которой работают io-игры и Colyseus:

- **Комната — единица работы.** Одна комната целиком живёт в одном потоке; 50 танков и сотни снарядов на 30 тиках/с — единицы миллисекунд из 33 доступных на тик, запас есть.
- **Много комнат — много потоков.** Внутри машины — `worker_threads` (потоки в одном процессе, с общей памятью при необходимости) или `cluster` / отдельные процессы (изоляция падений: упала одна комната — остальные живут). Один процесс-координатор раздаёт комнаты по воркерам.
- **Много машин — много регионов.** Координация через общее хранилище присутствия (Redis или аналог): какой воркер на какой машине держит какую комнату; клиент после входа в лобби получает адрес нужного процесса и подключается напрямую.
- **Сетевой ввод-вывод** в Node асинхронный и не блокирует тик; десятки тысяч одновременных соединений на машину — норма для `uWebSockets.js`.

Вопросы, которые надо закрыть замером, а не рассуждением: сколько комнат по 50 игроков тянет одно ядро при нашем протоколе; стоимость сериализации снимков на 50 клиентов; поведение при сборке мусора (паузы GC длиннее нескольких миллисекунд ломают тик — лечится отсутствием аллокаций в горячем цикле и переиспользованием буферов).

## Протокол и сериализация

| Вариант | Оценка |
|---|---|
| JSON | Просто, но в 3–5 раз объёмнее и медленнее бинарного. Допустим для лобби, не для снимков |
| MessagePack | Бинарный JSON без схемы. Компактнее JSON, но имена полей всё равно летят в каждом сообщении |
| Protobuf / FlatBuffers | Схема, генерация кода, компактно. Protobuf — компактнее, FlatBuffers — без разбора при чтении. Зависимость и этап генерации |
| **Своя упаковка через `DataView` по описанной схеме** | Максимальная компактность и скорость (поля фиксированной ширины, квантованные координаты и углы), полный контроль над дельтами. Схема — один модуль TypeScript, общий для сторон. Так устроен протокол diep.io | 

**Вывод.** Своя упаковка: сообщения игрового канала малы и однородны, выигрыш от схемных библиотек невелик, а контроль над битами нужен для дельт и квантования. Лобби — JSON по надёжному каналу.

## Компенсация задержки

Классическая схема (описана у Valve для Source и в статьях Gambetta «Fast-Paced Multiplayer»): предсказание своего танка на клиенте, сверка с сервером и переигрывание, интерполяция чужих с задержкой в один-два интервала рассылки. Для снарядов-объектов (не мгновенных попаданий) серверный «откат времени» для проверки попаданий не нужен — попадание считает движок по реальным позициям. Детали — в [тех-дизайне бэкенда](../tech/base/backend.md).

Риск, специфичный для нашего движка: снаряды летят быстро (до 700 px/с) и живут секунды; расхождение интерполяции чужого танка на 100 мс — это 20 px при скорости 220 px/с, что близко к радиусу танка (24 px). Визуально попадания «по краю» будут выглядеть спорно. Лечится квантованием времени рассылки и тем, что сервер прав всегда.

## Клиент

| Слой | Варианты | Оценка |
|---|---|---|
| Рендер боя | Чистый Canvas 2D (как в `tank-arena`), PixiJS (WebGL/WebGPU 2D), Phaser (целый игровой фреймворк) | Готовый рендер уже на Canvas 2D и справляется с полем 1600×900 и эффектами. Для 50 танков, камеры и мобильного — Canvas 2D достаточно, пока профиль не покажет обратное; PixiJS — запасной путь без смены модели данных. Phaser навязывает свою структуру игры и сеть не упрощает |
| Интерфейс вокруг боя | Голый DOM + TypeScript, Preact/Svelte (маленькие), React | Экранов мало (вход, лобби, настройка, итоги). Маленькая библиотека компонентов оправдана ради форм и списков; тяжёлый фреймворк — нет |
| Сборка | Vite | Стандарт де-факто для TypeScript-клиента, общие модули с сервером подключаются напрямую |
| Мобильные | PWA сейчас; Capacitor для магазинов потом | Браузер — база по требованиям |

## Прочее из постановки

- **Google-авторизация** — OAuth 2.0 / OpenID Connect на стороне лобби; сессия в cookie, игровой сокет получает короткоживущий токен при входе в комнату.
- **MySQL + Redis** — согласуется с требованиями; на критическом пути тика их нет.
- **Мониторинг** — стек Vector → ClickHouse → Grafana из `hw-all` переносится; альтернатива для одной машины — Grafana + Loki + Prometheus (легче по памяти, нет аналитических запросов по логам). Решение — при настройке инфраструктуры.
- **Античит** — не в первой итерации; авторитарный сервер и счётчик отброшенных команд — задел.

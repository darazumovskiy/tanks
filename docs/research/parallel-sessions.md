# Параллельные сессии агентов: как довести каждую до прода

Как вести много одновременных сессий агентов так, чтобы каждая доходила до выложенного кода, а не оставалась брошенной веткой, папкой или незакоммиченной правкой. Собрано 2026-10-07 по ревизии сессий за двое суток (скилл [session-audit](../../.cursor/skills/session-audit/SKILL.md)), истории репозитория и практикам команд, которые гоняют агентов параллельно.

## Главное

1. **Сессия — это разработчик.** У неё своя рабочая папка и ветка, своя карточка с состоянием, и она сама доводит работу до конца: посадка в `main` (в `main` попадает её коммит), выкладка, проверка на проде, уборка. «Сделал, но не залил» — не конец работы.
2. **Основная папка `../tanks` — не для правок.** В ней только читают: журналы, анализ, ответы на вопросы. Любая правка — в своей рабочей папке (`git worktree`). Почти все зависания за двое суток выросли из того, что сессии правили одну папку и видели незакоммиченные правки друг друга.
3. **Общее состояние — реестр в `.git/agents/`.** Это папка внутри общей для всех рабочих папок служебной папки git, в репозиторий она не попадает. Там карточки сессий («кто, что делает, в каком состоянии, чего ждёт») и аренды ресурсов. Аренда — запись «ресурс занят сессией X до такого-то времени»: если её не продлили, она истекает сама. Упавшая или брошенная сессия поэтому ничего не держит вечно. Пишет в реестр только скрипт и только под замком: занят замок — ждёт.
4. **Ресурсы трёх видов.** Одни копируются, и каждая сессия берёт свою копию: папка, порты, эмулятор Android, симулятор iOS. Другие существуют в единственном экземпляре и берутся в аренду: телефон оператора, выкладка на прод, посадка в `main`, внимание оператора. Третьи ограничены по мощности: процессор Mac под тяжёлые прогоны (сквозные тесты, покрытие, рой, эмулятор) делится на два слота.
5. **Посадка в `main` — по одной.** Сессия берёт аренду «посадка» и подтягивает свежий `main` в свою ветку. Затем дописывает документы задачи поверх свежего текста, прогоняет все проверки и отправляет в `main` без слияния: если `main` успел уйти вперёд, GitHub отклонит пуш. После этого она выкладывает на прод и проверяет. Выкладка на сервере защищена замком, две одновременные выкладки невозможны.
6. **«Жду другую сессию» не бывает.** Допустимы два ожидания. Первое — вопрос оператору: он записан в карточке и в последней строке ответа. Второе — занятая аренда: сессия ждёт её сама, повторяя попытку. Причины ждать соседа исчезают вместе с общей папкой.
7. **Конец хода проверяет хук.** Хук `stop` в Cursor срабатывает в конце каждого хода агента. Если в папке сессии лежит недосаженный код, а карточка не в состоянии «ждёт оператора», хук отправляет агенту сообщение «доведи или назови, чего ждёшь».
8. **Обзор для оператора — доска в браузере.** Локальная страница со всеми карточками: кто работает, кто ждёт оператора и с каким вопросом, сколько ждёт. Плюс уведомление macOS, когда сессия начинает ждать. Ревизия сессий читает те же карточки, а стенограммы смотрит только ради «сирот». Брошенную сессию может подхватить любой новый чат: в карточке и ветке есть всё, чтобы продолжить.

## Что сломалось за двое суток

По ревизии сессий 2026-10-06 (окно 48 часов, 21 чат Cursor, несколько сессий Codex):

| Что | Причина |
|---|---|
| Двойник: пять коммитов в ветке `twin` готовы, сессия остановилась | В основной папке лежали незакоммиченные документы соседней сессии, слияние их задело бы. Сессия ждала сигнала, которого никто не дал |
| Журнал клиента: коммит в ветке `battle-logs`, вопрос «сливать?» без ответа | Нет понятия «готово = выложено», сессия считала работу законченной на коммите |
| Дизайн боя толпы: около 28 файлов без коммита в `../tanks-design`, тронуты 43 часа назад | Сессия ждала просмотра вариантов оператором. Вопрос утонул в потоке других чатов, нигде не учтён |
| «Кто к нам заходит»: работа обещана, кода нет | Сессия ждала, пока соседняя закончит мультиплеер, и сигнал не пришёл |
| Коммит [0bce71c](https://github.com/darazumovskiy/tanks/commit/0bce71c) захватил 61 файл, включая чужие исследования и скилл | Все правили одну папку, и чужие файлы ушли прицепом. Теперь не восстановить, чей коммит что принёс |
| `docs/workflow/multiplayer/state.md` менялся в 45 коммитах из 143 за четыре дня | Состояние задачи — один файл на всех: главная точка конфликтов, сильнее любого кода |
| Разбор нагрузки на проде совпал по времени с выкладкой соседа | Выкладка перезапускает сервер. Замер, который этого не заметил, мерит не то |

Корни — пять: общая папка вместо своей; нет определения «готово»; ожидание соседа без механизма; общий файл состояния задачи; ресурсы без учёта занятости.

## Как это решают другие

- **Своя рабочая папка на агента, слияние по одной.** Своя папка снимает конфликты, пока идёт работа, но не при слиянии. Ветки сливают строго по очереди: подтянуть свежий `main`, прогнать все тесты, отправить без слияния. Если подтягивание дало конфликт или упали тесты, процесс останавливается, а не угадывает ([DEV: конфликты в рабочих папках агентов](https://dev.to/raylabs/handling-git-merge-conflicts-in-multi-agent-worktrees-1em8), [Context Wire](https://ctxwire.com/articles/git-worktrees-for-coding-agents/), [Agentic Blog](https://blog.appxlab.io/2026/04/01/parallel-ai-coding-agents-git-worktrees/)). Общие файлы, которые трогают все задачи (у них — `Cargo.toml`, роутинг), правят отдельным первым шагом ([DEV: worktrees](https://dev.to/battyterm/git-worktrees-changed-how-i-run-parallel-ai-agents-39pm)).
- **Очередь слияний.** У команд с GitHub это merge queue: ветка проверяется против того `main`, каким он будет после неё. Для потока меньше 5–10 слияний в день хватает ручной очереди по одной ([Trunk](https://trunk.io/blog/when-your-development-team-actually-needs-a-merge-queue), [Mergify](https://mergify.com/learn/merge-queue)). У нас слияний больше, но проверки идут локально, поэтому роль очереди играет аренда «посадка» плюс пуш без слияния.
- **Аренды вместо замков.** MCP Agent Mail даёт агентам аренду файлов со сроком. Аренды советующие (не запрещают, а предупреждают) и истекают сами, поэтому упавший агент ничего не держит; при коммите их проверяет хук git ([mcp_agent_mail](https://github.com/dicklesworthstone/mcp_agent_mail)). Claude Code в командах агентов ведёт общий список задач: файл на задачу, захват под замком на файле ([Agent teams](https://code.claude.com/docs/en/agent-teams)).
- **Рабочее место как единица.** Conductor и Vibe Kanban дают каждой задаче рабочее место: папка, ветка, чат, проверки, архив. Готовое сливают и архивируют, неготовое остаётся видимым в списке ([Conductor](https://www.conductor.build/docs/concepts/workflow), [Vibe Kanban](https://vibekanban.com/docs/workspaces/index)).
- **Cursor.** Cursor умеет создавать рабочие папки сам (`/worktree`, настройка в `.cursor/worktrees.json`), но кладёт их в `~/.cursor/worktrees`. С обычными командами `git worktree` они сочетаются плохо ([документация](https://cursor.com/docs/configuration/worktrees), [форум](https://forum.cursor.com/t/when-using-parallel-agents-with-a-window-opened-to-a-git-repos-child-folder-the-apply-button-doesnt-work/151613)). Хук `stop` получает номер чата и может отправить агенту следующее сообщение; число таких повторов ограничено ([hooks](https://cursor.com/docs/hooks)).
- **Документы-журналы.** Файлу, в который только дописывают, git может сливать строки обеих сторон без конфликта (`merge=union` в `.gitattributes`). Для файлов, которые переписывают на месте, это опасно: появятся дубли ([gitattributes](https://git-scm.com/docs/gitattributes), [разбор на DEV](https://dev.to/rulestack/two-writers-one-append-only-ledger-the-git-conflict-one-gitattributes-line-fixed-and-the-files-55j0)).

## Схема

### Жизненный цикл сессии

| Состояние | Что значит | Кто двигает дальше |
|---|---|---|
| `работает` | Пишет код в своей папке | Сама сессия |
| `ждёт оператора` | Нужен ответ, решение или руки оператора; вопрос записан в карточке | Оператор отвечает в этом чате |
| `ждёт ресурса` | Аренда занята; в карточке — кем и до когда | Сама сессия: повторяет попытку, по сроку аренды или после её освобождения |
| `сажает` | Держит аренду посадки: подтягивает `main`, проверяет, отправляет | Сама сессия |
| `выложено` | Код в `main`, на проде, проверен; папка и ветка убраны | — |
| `закрыто` | Работа брошена осознанно; в карточке — почему и что с веткой | Оператор решил |

**Готово** — это `выложено`. Чисто исследовательская сессия без кода заканчивается документом, который тоже прошёл посадку в `main`.

**Карточка** — `.git/agents/sessions/<имя>.json`: задача одной фразой, папка, ветка, номер чата (`conversation_id`), состояние, вопрос к оператору, что осталось сделать, как проверить, какие файлы и разделы сессия собирается трогать, занятые порты, время последнего обновления. Имя — короткое слово задачи, оно же имя ветки и папки: `twin`, `iphone-reconnect`.

### Рабочая папка

- Папку создаёт хук при первой попытке правки в основной папке: ветка от свежего `origin/main`, папка `../tanks-<имя>`, зависимости и сборка `shared`. Агент получает отказ с путём своей папки и повторяет правку там.
- Папка — рядом с основной, а не через `/worktree` Cursor: так её видят обычные команды git, Codex и ревизия сессий.
- Агент работает в своей папке по полным путям. Окно Cursor остаётся на основной папке: правила и скиллы читаются из неё.
- Коммиты — часто, в свою ветку. Ветка уходит на GitHub как резервная копия: у работы есть копия вне ноутбука, и её может подхватить другая сессия.
- Основная папка всегда равна `origin/main`. После каждой посадки её подтягивают только перемоткой вперёд (`git pull --ff-only`), своих правок в ней нет.

### Реестр и аренды

- **Где:** `$(git rev-parse --git-common-dir)/agents/` — общая для основной и всех рабочих папок, в репозиторий не попадает, переживает удаление рабочей папки.
- **Как:** маленькая команда на Node (Node есть всегда, `flock` на macOS нет): `npm run session -- …`. Руками и другими скриптами реестр не правится.
- **Замок реестра** держится доли секунды — на одно «прочитать, изменить, записать». Берётся созданием файла замка, который нельзя создать дважды (создание без перезаписи атомарно). Занят — команда ждёт и повторяет. Замок, чей владелец уже не работает (процесса с его номером нет), команда снимает сама.
- **Аренда** держится минуты и часы, пока сессия пользуется ресурсом. Это запись в реестре: кто держит, зачем, до когда. Чтобы держать дальше, аренду продлевают; истёкшую может забрать любой. Пример: «эмулятор занят сессией `iphone-reconnect` до 02:10, проверка переподключения».
- **Кто пишет:** карточки и аренды заполняют хуки и команда посадки, агент реестр не трогает. Устройство — тех-дизайн [agent-sessions.md](../tech/impl/infra/agent-sessions.md).

### Общие ресурсы

| Ресурс | Вид | Как работать |
|---|---|---|
| Рабочая папка, `node_modules`, сборки | копия | Своя у каждой сессии |
| Порты | копия | Тесты уже берут свободный порт: сервер печатает его при запуске. Ручной сервер для проверки или страницы просмотра — с портом из карточки, ссылку оператору — с этим портом |
| Эмулятор Android | копия | `emulator -avd tanks -read-only -port <чётный 5554–5682>` — копия того же устройства без сохранения состояния. Адрес для `adb` — `emulator-<порт>`. Запуск берёт тяжёлый слот, в конце сессия гасит свою копию |
| Симулятор iOS | копия | `xcrun simctl clone <база> <имя сессии>` — своя копия симулятора, в конце удаляется |
| Браузер для проверок | копия, с оговоркой | Playwright — свой браузер у каждого прогона. Браузер chrome-devtools MCP один на окно Cursor: сессия открывает свою вкладку и работает только с ней, чужие не закрывает |
| Процессор Mac | ограничен | Сквозные тесты, покрытие, рой, эмулятор — аренда `heavy`, два слота. Замер скорости на Mac — оба слота сразу, иначе цифры врут |
| Телефон оператора | один | Аренда `phone`. Брать её значит одновременно спрашивать оператора: телефон в его руках |
| Посадка в `main` | один | Аренда `landing` (ниже) |
| Прод: выкладка | один | Замок на сервере в `deploy-local.sh` (`flock` на Linux есть): вторая выкладка ждёт первую. Каждая выкладка ставит отметку на дашборде Grafana с коммитом |
| Прод: замер | один | Аренда `prod-measure`. Выкладка перезапускает сервер: если она случится посреди замера, цифры смешают две версии кода и паузу первого боя после перезапуска. Выкладку не запрещаем (выкладывать можно в любой момент), а замер в конце сверяет время запуска сервиса (`systemctl show tanks -p ActiveEnterTimestamp`). Сервер запускался во время замера — замер повторяется |
| Дашборд Grafana | один | Описание дашборда — код: попадает в `main` посадкой и заливается только из `main` |
| Внимание оператора | один | Вопрос — последней строкой ответа, хук переносит его в карточку. Обзор всех вопросов — на доске и в ревизии сессий |

### Посадка и выкладка

1. Всё закоммичено в своей ветке.
2. Аренда `landing` (срок 40 минут, продление на долгих проверках).
3. `git fetch` и подтягивание `origin/main` в ветку. Короткая ветка — перестройкой поверх `main` (rebase), длинная со множеством коммитов — слиянием `main` в ветку, чтобы решать конфликты один раз.
4. Конфликт решает сажающая сессия: её задача — сохранить и своё намерение, и чужое. Чужое намерение берётся из коммита и карточки соседа, а не угадывается. Если намерения несовместимы — аренда отпускается, вопрос уходит оператору.
5. Документы задачи — сейчас, поверх свежего текста: запись в `state.md`, строка в `decisions.md`, правка `INDEX.md` и `roadmap.md`.
6. Все проверки из `AGENTS.md`; сквозные — если задеты клиент, сервер или протокол.
7. `git push origin HEAD:main`. Отклонён — `main` ушёл вперёд, возврат к шагу 3.
8. Выкладка `deploy/deploy.sh`, проверка на проде по готовности фичи и ряд «Сервер: ОК?» на дашборде.
9. Аренда отпускается, карточка — `выложено`, папка и ветка удаляются, основная папка подтягивается перемоткой.

Номера по порядку — версия протокола, номер шага задачи — после подтягивания `main` пересчитываются на следующий свободный. Тесты протокола ловят, если два куска взяли один номер.

### Документы задачи без конфликтов

- `decisions.md` — журнал, в который только дописывают: в `.gitattributes` — `merge=union`, строки обеих сторон сохраняются.
- `state.md` — переписывается на месте, `union` для него опасен. Правится только при посадке, поверх свежего `main`: посадка останавливается, если ветка меняла код, а `state.md` не тронут. Между посадками состояние работы — в карточке: последний ответ агента и тронутые файлы туда пишет хук.
- `.cursor/tasks/current` — указатель на задачу живёт в каждой рабочей папке свой.

### Ожидание и конец хода

- Нужен оператор — последняя строка ответа `Жду тебя: <вопрос>`. Остальные состояния хуки выводят сами из фактов: есть ли непосаженное, занята ли аренда, прошла ли посадка.
- Хук конца хода по номеру чата находит карточку. Если в её папке есть незакоммиченное или коммиты вне `main`, а вопроса оператору нет, хук отправляет агенту «доведи до посадки или назови, чего ждёшь». Повторов — не больше трёх. Тот же хук есть у Codex (событие `Stop`).

### Обзор для оператора

- **Доска** — `npm run board`: локальная страница в браузере, сама обновляется из реестра. Сверху — сессии, которые ждут оператора: вопрос, сколько ждут, название чата. Ниже — работающие, ждущие ресурса, занятые аренды, карточки без движения дольше суток. Оформление — в стиле игры, но это инструмент команды, не экран игрока.
- **Уведомление macOS** (`osascript`), когда карточка переходит в `ждёт оператора`: вопрос не тонет среди чатов.
- Ревизия сессий начинает с тех же карточек. Стенограммы — только для сирот: папок и веток без карточки.
- Подхватить брошенное — `/adopt <имя>` в любом новом чате: сессия берёт карточку, последний ответ и ветку и продолжает.

## Что ещё учесть

- **Право на git.** Сейчас коммиты и пуши — только по прямой просьбе: так требуют ADR [process.md](../adr/process.md) и личное правило оператора. Оператор 2026-10-07 дал сессиям постоянное разрешение: коммитить в свою ветку, отправлять её на GitHub, сажать в `main` по процессу и выкладывать. ADR и личное правило меняются первым шагом внедрения.
- **Внимание оператора — самый дефицитный ресурс.** Десять сессий задают десять вопросов в разных чатах. Вопрос, который не попал в карточку, теряется — так потерялись просмотр вариантов дизайна и сигнал для «кто к нам заходит».
- **Режем на куски, которые можно посадить.** Сессия на 15 часов копит отставание от `main` и риск потерять работу. Законченный кусок сажается сразу, даже если фича целиком ещё не готова. Законченный — значит проверенный и точно работающий: выполнено определение готовности из `AGENTS.md` (план тестов исполнен, все проверки зелёные, видимое игроку проверено в браузере). Непроверенное в `main` не попадает.
- **`main` подтягивается при каждом возобновлении.** Ветка дизайна отстала от `main` на 46 коммитов за сутки. Подтягивать свежий `main` в начале каждого хода после паузы дешевле, чем один раз перед посадкой.
- **Одни файлы — по очереди.** Хук записывает в карточку каждый тронутый файл. Сессия тронула файл, который правит и другая работающая сессия, — хук сразу говорит агенту, какая: кусок с общими файлами сажается первым, остальное — после.
- **Саб-агенты одной сессии — в её папке.** Параллельно только на разных файлах, как в скилле [develop](../../.cursor/skills/develop/SKILL.md). Своя папка нужна только независимой задаче.
- **Уборка.** Папки и ветки удаляются при посадке. Доска показывает истёкшие аренды и карточки без движения дольше суток — это кандидаты в ревизию.
- **Codex и Cursor — один процесс.** У Codex есть хуки с теми же событиями (перед действием, после, сообщение пользователя, конец хода — [документация](https://developers.openai.com/codex/hooks)). Логика процесса пишется один раз, к каждому инструменту — тонкий переходник формата.

## Почему процесс на хуках

Агент над сложной задачей не должен держать в голове процесс: каждое правило в контексте отнимает внимание у задачи и может забыться к сотому шагу. Поэтому всё, что проверяется по фактам, делает код, а агент знает три правила.

| Инструмент Cursor | Роль в процессе | Почему так |
|---|---|---|
| Хуки | Основа: создают папку, запрещают правку основной папки и пуш мимо посадки, берут аренды, ведут карточку, не дают закончить ход с непосаженным | Срабатывают на каждом действии сами, агенту ничего не нужно помнить. Отказ объясняет агенту, что делать, ровно в момент ошибки |
| Команда `npm run land` | Вся посадка и выкладка одной командой | Двадцать шагов посадки агент не держит в голове: команда останавливается с понятным выводом и продолжает после исправления |
| Хуки git | Запрет коммита в основной папке и пуша в `main` мимо посадки | Ловят то, что прошло мимо хуков агента: сбой хука, ручной запуск, другой инструмент |
| `AGENTS.md` | Три правила агента | Читают и Cursor, и Codex |
| Скиллы | `develop` — как делать работу; `current-task` — документы задачи; `session-audit` — ревизия | Процедуры, которые требуют суждения, а не проверки фактов |
| Команда `/adopt` | Подхватить брошенную сессию | Короткий вызов для оператора |
| `worktrees.json` | Настройка папок, которые создаёт сам Cursor | Одна настройка для любых папок |
| MCP | Не используется для процесса | Инструменты MCP добавляют агенту новых действий, о которых надо помнить; хуки и одна команда покрывают всё |

Хук отказывает и называет путь своей папки, а не подменяет путь незаметно (подмена ввода хуки умеют). При подмене ссылки в отчётах агента вели бы на основную папку, где правок нет, а вывод команд расходился бы с тем, что агент думает о путях.

Папки сессий лежат рядом с основной (`../tanks-<имя>`), а не в папке рабочих копий Cursor (`~/.cursor/worktrees`). Cursor сам удаляет старые копии сверх 25 на машину, и непосаженная работа могла бы пропасть ([документация](https://cursor.com/docs/configuration/worktrees)).
